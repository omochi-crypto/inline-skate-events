# 大会情報収集システム 現行設計

設計版：2026-11-02 review-2。対象は `omochi-crypto/inline-skate-events` と大会調査・稼働監視タスク。

## 1. 目的と変更できない条件

少ない取得で大会を発見し、根拠を確認して、人が承認した情報だけ公開する。調査先への配慮を網羅性・更新速度より優先する。

- 大会掲載・既存大会の変更公開は大会ごとの明示承認を要する。情報源採用の承認とは別に扱う。
- 定期ChatGPTタスクは報告専用。Issue作成・情報源登録・承認・公開をしない。
- 個人・小規模サイトは採用済み対象のみ7日以上空け、入口1ページと不可欠な資料1件まで。
- 拒否・認証異常・取得条件不明を回避しない。失敗・未取得を候補ゼロと混同しない。
- テストは架空データ・取得済みデータで行い、実在大会をテスト承認しない。天気用リポジトリを変更しない。

## 2. 構成と責務

| 担当 | 入力→処理→出力 | 行わないこと |
|---|---|---|
| Actions check | コード→オフライン回帰テスト→結果 | 外部巡回 |
| Actions collect | 承認済み取得設定＋永続状態→予約・上限内取得・抽出→候補/警告/差分/指標 | 大会公開、情報源の自動採用 |
| ChatGPT＋調査Skill | 最新の完了実行・保存済み情報＋公開検索→一次照合・重複確認→判断候補 | 定期実行からのGitHub書込、制限回避 |
| Work | 設計・実装・障害分析。別途個別承認された公開操作を代行 | 一般的な作業継続指示を大会承認に読み替えること |
| 利用者 | 根拠付きの大会/変更/情報源候補→対象ごとの判断 | GitHubやJSONの手動操作は原則不要 |

起動予定はActionsが月水金10:25 JST、調査が10:45 JST、監視が毎日11:30 JST。開始時刻だけで前工程の完了を推定しない。最新run_id・終了状態・収集レポートを一度確認し、未完了なら前回結果と未確認範囲を明示する。短間隔ポーリング・自動的な追い付き巡回をしない。

## 3. 取得の上限と対象確認

| 制御 | 現行値/動作 | 境界・限界 |
|---|---|---|
| 設定検証 | HTTPS・資格情報なし、ID/URL重複なし、取得間隔・小規模指定・adapterを検査 | 不正ならGitHub APIも調査先も呼ばない |
| 小規模対象 | 1ホスト1入口。ホスト単位の次回期限を永続化 | 設定IDを変えても7日の間隔を短縮しない |
| 頻度 | 基本公式一覧は48時間以上、小規模と補完用の種目別一覧は7日以上 | 月水金は起動機会。期限内は保存済み観測を再利用 |
| 移行 | 小規模サイトの取得履歴が無い初回は1週間の静穏期間 | 未取得を正常に全件調べたとは表示しない |
| 同時数・間隔 | 全取得逐次。同一ホストは応答終了後10秒以上、長いCrawl-delayを優先 | 60秒超の待機が必要ならその回は取得を控える |
| 要求数 | source単位3（小規模）/5（その他）、同一ホスト合算3/8、1実行合算24まで | robots・失敗要求を含む。beginや別設定でリセットしない |
| 取得量 | HTML/PDF各2MB、robots 512KB（各超過検出用1byteを追加）。1実行の読取予算は検出byte込み10MB | timeout等で読取量が不明なら予約した読取上限を消費した扱いにする。TCP等の全転送量ではない |
| 再試行・転送 | 自動再試行なし。転送/他ホスト/HTTPへの自動追跡なし | 必要な正規URLが変わった場合は別途確認する |

robotsを先に確認し、禁止・不明・拒否は停止する。現在のパーサーはAllow例外でDisallowを緩和しない保守的な実装であり、一部を過剰停止する可能性がある。空のUser-agent・不正制御文字・曖昧な禁止パス等も保留する。robots許可だけでサイトの利用条件をすべて確認したとは扱わない。

401/403/429/5xx、認識できるアクセス確認画面等はホスト停止として保存する。Retry-Afterは記録するが、時間経過だけで自動解除しない。検出できない確認画面が存在し得るため、正常HTTPコードだけで内容を正常としない。

週1回は本システムの保守的な運用値で、一般的な包括許可ではない。サイトの条件・管理者の要請を優先する。新しい情報源を自動追加しない。個人ページの共有履歴を参照できないChatGPT実行では、直接取得をせず保存済み情報・公開検索を使う。

## 4. 永続状態と失敗時の挙動

`collection-state`ブランチのstate.jsonを使う。本文全文は保存せず、解析済み観測・取得時刻・設定指紋・次回期限・停止理由を保持する。

1. stateブランチの先頭SHAを読み、そのSHAに固定して内容を読む。構造・時刻・版を検証する。
2. 取得対象と期限を一括予約し、状態を保存できてから外部取得を始める。小規模ホストの期限も予約する。
3. 予約された対象だけ取得する。取得失敗・取得時刻不明・期限切れの保存済み観測は参考情報へ隔離し、新規Issueや更新候補の自動処理に使わない。
4. 観測・停止状態をまとめて保存する。ref更新は非fast-forwardを拒否し、競合時に再試行しない。
5. 結果保存が失敗した場合は、前に保存した未完了予約が次回の取得を止める。診断を残し、Issue操作も停止する。

旧5項目の設定指紋からの移行は、同一URL・抽出設定の場合に限り1回の保守的な静穏期間を置く。旧版というだけで永久停止させず、取得量も増やさない。

状態JSONは750KBで保存を止める。状態が壊れていれば外部取得しない。設定のURL・抽出方法・頻度/小規模指定が変わった場合、古いキャッシュを新設定へ流用せず停止して確認する。

取得のある回は原則予約/結果の2状態コミットを要する。状態書込権限は実行ジョブに限定するが、GitHubのcontents:write自体をstateブランチだけに限定できたとは主張しない。コード側の固定ブランチとレビューで範囲を制限する。

途中停止・破損・制限による停止を無条件に解除する復旧処理は設けない。原因を確認できるまでは取得を控える。Workではログと状態を読み、制限回避にならない復旧案を自律的に検討できる。分からない状態を勝手にリセットしない。

## 5. 観測・重複・変更の扱い

- 候補にはsource_ids、根拠URL/断片、取得日時、観測の完全性を残す。公開項目への自動転送はしない。
- 同じIDでも日付・会場等の相違を確認する。取得失敗由来の古いキャッシュを、利用可能な観測より優先しない。
- Issueは番号の古い順に統合し、APIの並び順による過去データへの巻き戻りを防ぐ。承認済み情報を比較の基準に優先する。
- 旧Issue本文JSON、open/closed、承認済み、見送り履歴を照合する。closedだけで採否を断定しない。
- 新規、重複、重要変更、別名/改期疑い、情報衝突、未検証観測を分ける。別名/改期は自動統合しない。
- 月だけの日付、年省略、締切、予備日、過去の参加報告は確認対象とし、将来開催を推測しない。

`review-required.json`へ根拠付きで出力し、ChatGPTが一次資料と照合して利用者へ提示する。抽出器が中止や申込条件の変更をすべて理解できるとは主張しない。

## 6. 公開更新と既存情報の保護

更新提案は、変更部分だけを既存データへ直接上書きしない。

1. `prepare_revision(previous, changes, remove=...)`で既存項目を保持した完全な提案を先に作る。
2. 変更前後・明示的な削除・根拠・不明点を利用者へ提示する。
3. 対象大会の明示承認を受け、最新Issueと更新前digestが変わっていないことを確認する。
4. 完全な提案のdigestへ結び付いた所有者の承認コメントで処理する。承認後に提案を補完・マージしない。
5. 前の公開内容・承認証拠をapproval_historyへ残す。古い更新前digest、暗黙の項目削除、空欄による削除、変更のない再承認は拒否する。

削除はremoved_fieldsに明示し、その項目は提案から除く。大会ID・名称・日付・種目・都道府県・会場の削除は禁止する。公開には会場名が必要であり、未確定なら候補を保留する。中止情報も通常の再承認を要する。

## 7. レポートと運用監視

収集開始時に古い候補スナップショットを空にし、初期レポートを出す。状態読み込み・予約・取得・結果保存のどこで失敗したかを残す。書込可能なローカル領域がある場合は、異常終了でも診断レポートを保存する。

safe_for_issue_writeは「今回の状態を保存し、Issue処理へ進めるか」を示し、全情報源が正常という意味ではない。falseならIssue操作を禁止する。個々の失敗キャッシュは別途隔離する。

指標はrun_id/コードSHA、HTTP要求数、取得できた本文量と不明読取分の予算消費、取得時刻、キャッシュ・未取得・エラー件数、候補分類、Issue新規/重複/繰越。サーバーCPUや完全な通信量、通知到達を測定したとは扱わない。

pushのcheck成功とscheduleのcollect成功、データ保存とWeb公開、実行完了と調査完了を分ける。同じ障害の反復コメントを避け、状態の変化と復旧を残す。

## 8. 検証・リリースの条件

- 修正前の反例を先に実行し、失敗を確認してから実装する。
- オフラインテストで、更新時の情報保持・明示削除・古いdigest拒否、共有上限、設定変更キャッシュ拒否、古いIssue、失敗観測隔離、異常レポート、状態競合を確認する。
- 再レビューでは「設定の重複・欠損」「既存機能との互換性」「実行全体の失敗」を確認し、モック環境で予約→取得→抽出→報告の連携を検証する。
- GitHubのcheckを確認し、外部巡回は試験目的で追加起動しない。次の通常実行を既存監視で確認する。
- 既存4大会のJSONと承認digestは維持する。実在大会をテスト承認しない。

## 9. 未実装・未確認の範囲

ETag/Last-Modified、完全なIssue差分同期、運営者の別ドメインをまたぐ予算統合、地域ローテーションの永続記録、すべてのアクセス確認画面の検出、全サイトの利用条件、ChatGPT定期環境からのSkill/Artifact利用、改修後の実サイト巡回・通知到達は別途確認が必要。取得上限の範囲外へ広げて補完しない。
