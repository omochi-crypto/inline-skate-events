# 専門レビュー・修正記録

対象コミット：fda862062d2d6131e2ef0e93a8fcf860c461a94d。レビュー方法は、設計とコードの照合、反例テスト、失敗時の追跡、修正後の再レビュー。外部サイトへの負荷試験はしない。

## 初回レビュー

| 指摘 | 重要度 | 修正前に確認した反例 | 修正方針 |
|---|---|---|---|
| 更新時の詳細消失 | 高 | 一部項目だけの更新で、既存details/申込案内が消える | 完全な提案を承認前に作り、暗黙削除を拒否 |
| サイト上限の再初期化 | 高 | beginを別設定で呼び直すと取得上限をリセットできる | ホスト/実行合算を共有し、重複設定も拒否 |
| 設定変更後の誤キャッシュ | 高 | URLを変えても旧URLの観測が返る | URL・抽出/取得ポリシーを指紋化し、変更時は保留 |
| 古いIssueへの巻き戻り | 中 | API順によって古いIssueが新しい候補を上書き | Issue番号順で比較し、承認済みを優先 |
| 失敗観測の候補化 | 高 | 失敗時の保存済みイベントもnewと分類される | 完全性を引き継ぎ、未検証観測として隔離 |
| 障害時の診断欠落 | 高 | 予約保存の失敗でレポートが無く、古い候補が残る | 初期レポートと失敗フェーズを保存、Issue操作を停止 |

上記6ケースは修正前の実装に対して実行し、5件の失敗と1件のレポート欠落エラーを確認した。架空データとモックのみを使用した。

## 設計改訂後の再レビュー

完全な更新提案を保存するだけでなく、空欄を使った削除、公開会場の欠落、sourceの重複/方針変更、状態破損・競合、モック環境での一連の実行を追加の検証対象とした。読取途中のtimeoutで取得量が分からない場合の保守的な予算消費、旧版状態の一度限りの静穏移行、期限切れキャッシュの隔離も確認した。コード内の注意書きだけでなく、公開更新・取得開始の前に機械検査を入れる方針を採った。

古い記述の追記を増やす形をやめ、[現行設計](design.md)を一つの基準にした。初期調査の数字や過去の「未実装」は、現行の保証と混ぜない。

## 検証結果

ローカルのPython53テスト、JavaScript画面チェック、構文検査とdiff検査を通過。モックで予約の保存前に外部取得しないこと、結果保存失敗時に未完了予約と診断が残ること、再実行で外部取得・状態コミットが増えないことを確認した。既存4大会のデータと承認digestは不変で、公開ビルドも成功。GitHub上の検証結果は反映後に確認する。実サイトへの追加巡回と実在大会の承認は行わない。
